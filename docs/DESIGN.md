# Design notes

Decisions that are settled, and the reasoning behind them.

Terms — issuer, user, agent, wallet, verifier — are as defined in the README.

## Keys

| Key | Job | Frequency | Protection |
|---|---|---|---|
| Issuer | Signs the ID credential | Often | SoftHSM via PKCS#11 |
| `sk_U` (user root) | Signs delegations | Rarely, user present | Software file |
| `sk_S` (wallet) | Signs presentations | Constantly, unattended | Software file |

All three are ML-DSA-44. The system is post-quantum end to end.

**Why software is enough for `sk_S`.** Delegation bounds the damage. A stolen
`sk_S` allows presentations to the delegated audiences until the delegation
expires. It does not allow permanent impersonation.

**Why `sk_U` is software too.** A consequence of going ML-DSA-only. Commodity
tokens do not ship ML-DSA yet — Yubico has prototypes, not products — so a real
hardware token for `sk_U` is not available. This is a finding worth reporting:
PQ migration is blocked at the edge by hardware availability, not by the
algorithms.

## Delegation

Follows `draft-gco-oauth-delegate-sd-jwt-00`. The delegation is not a separate
artifact; it *is* the KB-JWT of the ID credential, made selectively disclosable
in its own right. One chained wire format:

```
<SD-JWT>~~<KB-SD-JWT>~<KB-JWT>
```

Verification walks the chain: the issuer's key verifies the first link, and the
`cnf` claim of each link supplies the key for the next.

### Binding is `issuer_jwt_hash`, not `sd_hash`

`sd_hash` covers the preceding SD-JWT *and its disclosures*, freezing the
disclosure set at delegation time. `issuer_jwt_hash` covers only the
issuer-signed JWT. Using it means the user hands the wallet the credential plus
all disclosures and does not have to predict which claims a future verifier will
ask for; the wallet decides at presentation time.

That is the requirement here: the user is delegating the whole job of credential
handling, not pre-authorizing specific redactions.

### Audience scope

Delegations carry per-audience scope in `delegate_payload`, one payload per
audience, each with its own `aud`, claim allow-list and `exp`. The wallet
discloses the one matching the verifier in front of it, so the wine shop does
not learn the pharmacy was also authorized.

The simpler alternative is a single payload with a disclosable `aud` array,
which hides the other audiences equally well. It was not chosen because every
audience would then share one allow-list and one `exp`. Per-audience scoping is
what lets the wine shop be limited to `over_18` while another verifier gets
more, and that granularity is the point of the policy engine.

One `sk_U` signature covers the whole set, which matters because `sk_U` signs
only with the user present.

This is also what makes software storage for `sk_S` defensible: the audience
restriction is signed by the user and checked by the verifier, not merely
enforced by a policy file sitting next to the stolen key.

### The final KB-JWT is where `sk_S` does its work

The last component of the chain is an ordinary KB-JWT, signed by `sk_S`, freshly
per request. It covers the verifier's nonce and the verifier's identity.

Both halves are needed and they defend against different things. The nonce stops
replay: a presentation captured off the wire cannot be sent again, because the
next request carries a different nonce. The audience binding stops the wine shop
from taking a presentation it legitimately received and reusing it against the
pharmacy.

## Decisions log

Small choices with no other natural home.

- **Rust edition 2024, no declared MSRV.** The post-quantum crates move fast
  and promising an old compiler would only get in the way. CI tracks stable.
- **`unsafe_code = "forbid"` workspace-wide.** The PKCS#11 work in section G
  goes through `cryptoki`, which holds the unsafe FFI on its side. If that
  turns out to be wrong, soften to `deny` and allow it at the one site that
  needs it.
- **Ed25519 is the test-only algorithm, not ECDSA.** EdDSA is deterministic, so
  the RFC's EdDSA examples can be regenerated byte for byte. The ECDSA examples
  are verify-only.
